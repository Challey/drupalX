## 1. 一句话定位（升级后）

**DrupalX = 开源框架底座上的策展式应用生态 + 交钥匙交付操作系统。**

- **现在**：以政企门户交钥匙为主战场（既有主线不变）。  
- **方向**：架构面向**全行业 + 个人**可扩展；个人用户平台作为后续波次开通，不阻塞政企交付。  
- **开放**：框架源码对外公开；对外只公开**开发接口与方法**；**完整库与深度文档**仅对**审核通过并签署协议**的平台开发参与者开放。  
- **应用**：开发者上架应用对**平台与使用用户**提供源码可读/可改（自用）；**禁止使用者向第四方泄露或再开放**——写入协议与许可条款。

## 2. 战略调整要点

| 维度 | 现行 | 升级后 |
|------|------|--------|
| 受众 | 政企交钥匙为主 | **全行业 + 个人**为长期方向；**当前执行面仍以政企为主** |
| 开源叙事 | 底座 Drupal / GPL；商店策展半封闭 | **框架公开开源** + **应用源码对用户 reciprocal** + **反第四方扩散协议** |
| 开发者关系 | 认证上架 / 分成 | 分层：**公开 API** vs **认证库/文档金库** |
| 文档 | 仓库内 docs 基本同权 | **文档分级**：公开 / 注册 / 认证签署 / 运维内部 |
| 商店 | 苹果式策展（保留） | 策展保留；增加 **DX-RAL 许可确认** 与源码可见性字段 |

现行五性、Theme Studio、DXEP、交钥匙流水线、trust tier **全部保留**，上移为生态约束，而非被开源叙事替代。

## 3. 受众波次（架构先对齐，产品后开放）

```
Wave G/E（当前）  政府 / 企事业 / SME 子集套餐
        │
        ▼
Wave I（下一）    全行业 recipe / 垂直 packs（不改隔离模型）
        │
        ▼
Wave P（后续）    个人 / 创作者轻量租户（配额更小、信任默认更严）
```

### 3.1 租户类型（建议字段，确认后落地）

| `tenant_kind` | 说明 | 当前产品开关 |
|---------------|------|----------------|
| `gov` | 政务 | **开启**（默认 trust 收紧） |
| `enterprise` | 企事业 | **开启** |
| `industry` | 行业站（制造/零售/服务…） | 开启（recipe 已有） |
| `personal` | 个人 / 创作者 | **架构预留，产品默认关闭** |

工程原则：开通、配额、trust、计费、交钥匙蓝图均以 `tenant_kind` 分支；**禁止**为个人用户另建一套平行代码树。

## 4. 开源与可见性四层模型（核心）

```
┌─────────────────────────────────────────────────────────────┐
│ L0  Public Framework（公开框架）                             │
│     框架源码仓库 · 公共 DXEP/OpenAPI · 扩展接口说明            │
└────────────────────────────┬────────────────────────────────┘
                             │
┌────────────────────────────▼────────────────────────────────┐
│ L1  Public Developer Surface（公开开发面）                   │
│     Hooks / Events / DXEP 方法 · App 提交契约 · 示例          │
│     ✗ 不含内部库全文、打包密钥、运维手册、未审包               │
└────────────────────────────┬────────────────────────────────┘
                             │ 审核 + 签署协议
┌────────────────────────────▼────────────────────────────────┐
│ L2  Certified Partner Vault（认证金库）                      │
│     完整内部库 · 深度架构/打包/安全文档 · 私有 Composer 源      │
└────────────────────────────┬────────────────────────────────┘
                             │ 商店安装 / 许可
┌────────────────────────────▼────────────────────────────────┐
│ L3  Tenant App Source（用户可见应用源）                      │
│     已购/已启用应用：对平台 + 该租户开放源码（自用修改）        │
│     协议禁止向第四方再分发 / 公开镜像 / 旁路上架               │
└─────────────────────────────────────────────────────────────┘
```

| 层 | 谁可见 | 典型内容 | 许可/协议 |
|----|--------|----------|-----------|
| L0 | 任意访客 | Foundation 框架源码、公开 README、DXEP OpenAPI | 框架开源许可（见 §5） |
| L1 | 任意访客 / 注册开发者 | 扩展 API、提交规范、公开示例 | 同上 + 贡献者条款 |
| L2 | **认证开发者**（审核通过 + 签署） | 完整库、内部 docs、私有包源 | 开发者参与协议（DPA） |
| L3 | **平台 + 安装该应用的租户** | 上架应用源码树 / source bundle | **DX-RAL**（反第四方） |

**明确不对公众开放的：** 控制面运维密钥、证书私钥、租户数据、未上架草稿、认证金库文档、真实签名物料。

## 5. 许可与协议设计（必须写进条款）

### 5.1 法律现实（先说清，再选方案）

Drupal 核心及大量 PHP 模块衍生作品受 **GPL-2.0+** 约束：获得源码的人通常拥有再分发权利。  
因此「对用户开源、但禁止向第四方泄露开放」**不能**仅靠在纯 GPL 模块上叠一句「禁止再分发」来对抗 GPL；需要 **许可分层 + 合同 + 产品门禁** 组合。

### 5.2 推荐默认（请拍板 O1）

**O1-B · 双包拆分（推荐）**

| 包类型 | 形态 | 许可 |
|--------|------|------|
| 框架公开层 | DrupalX Foundation 公开仓库 | 与 Drupal 兼容的开源许可（GPL-2.0+ 或对非衍生部分 Apache-2.0，见 O2） |
| 商店应用 · 适配层 | 薄 Drupal 模块（路由/权限/配置） | GPL-2.0+（履行开源义务） |
| 商店应用 · 业务库 | **非 Drupal 衍生**的业务逻辑包（SDK/服务） | **DX-RAL**（源码对租户可见，禁止第四方再开放） |
| 平台金库 | 内部库与深度文档 | 版权保留 + DPA；不公开 |

辅以：

1. **开发者参与协议（DPA）**：认证前强制签署；违约可吊销 L2 访问与上架权。  
2. **租户安装确认**：启用应用前勾选 DX-RAL（禁止向第四方提供源码、公开镜像、二次上架）。  
3. **产品门禁**：源码下载需租户管理员身份 + 许可绑定；水印/审计下载日志。  
4. **商店违约处置**：发现第四方泄露 → 停更、撤许可、开发者连坐审核。

备选：

- **O1-A**：全部商店包纯 GPL；仅用 **ToS + 账号制裁** 约束第四方行为（法律约束力弱于许可分层）。  
- **O1-C**：平台自有模块双许可（社区 GPL / 商业 DX-RAL），第三方应用仍走 O1-B。

### 5.3 DX-RAL（草案要点 · 非法务终稿）

> 正式文本需法务审定；此处定产品意图。

1. **授权对象**：平台运营方；以及已合法安装/购买该应用的租户主体。  
2. **授权范围**：为该租户自身业务查看、修改、运维；可在本平台控制面内使用。  
3. **禁止**：向**第四方**（非平台、非本租户授权人员）提供源码、构建产物、内部文档；禁止公开 Git 镜像、二次分发、绕过商店上架。  
4. **修改回流**：鼓励经平台提交换代版本；不强制（除非另选 copyleft 变体）。  
5. **终止**：违约或许可到期后停止更新与源码下载；已安装实例的处理规则另定（建议：继续自用运行，但失去 L3 下载与支持）。  
6. **与 GPL 的关系**：若某文件依法必须 GPL，则以 GPL 为准；DX-RAL 适用于明确标注的非衍生业务包与文档。

### 5.4 开发者参与协议（DPA）要点

- 身份核验与安全责任；禁止上传恶意/侵权代码。  
- 上架应用须对平台与终端用户提供 L3 源码包。  
- 不得将 L2 金库内容泄露给未认证第三方。  
- 分成、审核、下架、安全响应 SLA。  
- 适用法律与争议解决（待法务）。

## 6. 文档与源码权限矩阵

| 资源类别 | 匿名公开 | 注册开发者 | 认证签署（L2） | 租户管理员 | 平台运维 |
|----------|:--------:|:----------:|:--------------:|:----------:|:--------:|
| 框架源码（L0） | ✓ | ✓ | ✓ | ✓ | ✓ |
| 公开 API / DXEP OpenAPI | ✓ | ✓ | ✓ | ✓ | ✓ |
| 入门与扩展指南 | ✓ | ✓ | ✓ | 只读 | ✓ |
| 深度架构 / 打包 / 安全手册 | — | — | ✓ | — | ✓ |
| 私有 Composer 库 | — | — | ✓ | — | ✓ |
| 已安装应用源码（L3） | — | — | 若亦为该应用开发者 | ✓（本租户） | ✓ |
| 证书私钥 / 租户数据 | — | — | — | 本租户数据 | ✓ |

实现落点（确认后）：

- 文档站点或 `docs/` 发布管线打标：`visibility: public | partner | internal`。  
- 伙伴文档走认证门户（Cookie / OAuth / 签名 token），校验 DPA 版本。  
- 源码：公开 monorepo（L0/L1）+ 私有 `partner` 远程（L2）+ 租户「应用源码」下载 API（L3）。

## 7. 与现行策展商店的关系

苹果式半封闭 **不取消**：

| 保留 | 加强 |
|------|------|
| 认证提交 → 审核 → lock/白名单 → 许可启用 | 上架必选 DX-RAL + 源码包齐备 |
| 政务 trust tier 收紧 | `tenant_kind=personal` 默认更严 |
| 禁止租户任意旁加载 | L3 下载 ≠ 允许旁路上架 |

更新 [module-curation.md](module-curation.md)：增加 `source_policy`、`license_family`、`dpa_required` 字段。

## 10. 成功标准

1. 外人能克隆/浏览 **框架公开源码** 与 **公开 API 文档**，但拿不到认证金库。  
2. 未签署 DPA 的开发者不能访问 L2 库与深度文档。  
3. 租户安装应用时必须确认「禁止向第四方泄露开放」；确认前不可用 L3 下载。  
4. 目录与实体能区分 `license_family=gpl|dx_ral|dual`。  
5. `tenant_kind=personal` 可在配置中存在且默认关闭，不影响政企开通。  
6. 法务可审的 DX-RAL/DPA 草案已入库并版本化。
